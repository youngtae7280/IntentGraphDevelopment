# P9.27 Diff-Backed Guided Proposals Review

## Decision

P9.27 passes its bounded product slice.

The normal Workbench path can now create a code-bearing, non-applied proposal from an
existing work request and declared mapping. This is materially closer to daily use
than P9.21's requirement-only proposal form because the graph stage and code-node
inspector now carry the actual proposed change.

## Acceptance Evidence

- 21 loopback server probes pass, including form contract markers, one digest-backed
  guided diff, projection reload, durable revisions, and unchanged snapshot provenance.
- 8 repeatable negative probes reject an empty diff list, an unmapped fact, duplicate
  fact diffs, malformed headers, stale context, out-of-range hunks, no-op diffs, and
  inconsistent hunk counts.
- The positive negative-probe baseline maps two facts but changes only the one carrying
  a diff, proving mapped context is not mislabeled as changed.
- The static P9.27 Workbench validates with 8,189 nodes, 7,996 relations, three code
  diffs, and four durable stages for the CSD cancellation proposal.
- Browser QA opened the proposal stage, observed `+2 nodes / 3 changed / 3 diffs`, and
  selected `CsdBrowseService.BrowseFolder`; its source provenance and exact diff were
  visible in the inspector.
- A separate browser form test selected one of three mapped facts, entered a real hunk,
  submitted without proposal JSON, reloaded the live Workbench, and observed one code
  diff. After the accuracy correction, only that diff-backed fact is classified as
  changed.

## Quality Findings Resolved During Review

1. The first server smoke exposed a bytes/string mismatch in deterministic diff-ID
   generation. The implementation was corrected and the full smoke rerun.
2. The first form submission revealed that all mapped facts were shown as changed even
   when only one had a diff. P9.27 now treats undiffed mapped facts as context and uses
   only diff-backed fact IDs for `changedNodeIds`.

## Preserved Boundaries

- target repository mutation: false
- nested snapshot mutation: false
- automatic code application: false
- graph-delta application: false
- verification/evidence execution: false
- approval automation: false
- network/provider/credential access: false

## Remaining Product Gap

The Workbench can author and inspect a real proposal, but it still cannot import a
typed build/test/runtime result through the normal UI and bind that result to a
proposal requirement. That is the next highest-value daily workflow gap.
