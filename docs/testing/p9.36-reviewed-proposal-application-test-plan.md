# P9.36 Reviewed Proposal Application Test And Validation Plan

Status: completed G1 plan-only. No target source mutation is allowed.

## Test Thesis

Before IGD implements source application, its contract must prove that one exact,
human-approved, snapshot-bound C# diff can be staged, applied, verified, refreshed,
and recovered without implicit authority or ambiguous source/overlay state.

## P9.36 Plan Validation

The plan-only slice must validate:

- product contract, test plan, prior-art decision, review, and roadmap links exist;
- P8.39-P8.46 are inventoried as an experiment, not copied as a product contract;
- Git usage is explicitly excluded from the G2 target write path;
- the first scope is one existing mapped `.cs` file and all excluded path classes are
  named;
- source, proposal, approval, evidence, transaction, refresh, rollback, and
  Workbench records have exact identity bindings;
- source application remains false in every P9.36 artifact.

## G2 Required Positive Scenarios

| ID | Scenario | Required result |
|---|---|---|
| A01 | exact one-file approved proposal | staged candidate, one atomic replacement, source after-digest, refresh activation, receipt, and history agree |
| A02 | accepted verification evidence | evidence is bound to the exact proposal and isolated after-source candidate |
| A03 | post-apply refresh | active revision source digest equals the live after-source digest |
| A04 | explicit rollback | exact preimage is restored and a recovery/history record is present |
| A05 | restart after completed transaction | journal/receipt validation reports one truthful completed state |

## G2 Required Fail-Closed Scenarios

Every failed scenario must record source bytes, active revision, and journal state
before and after the attempt.

| ID | Invalid state | Required result |
|---|---|---|
| N01 | missing or wrong plan/approval digest | zero target write |
| N02 | AI, verifier, or evidence decision treated as apply authority | zero target write |
| N03 | stale proposal, mapping, source, file, workspace, launch, or candidate digest | zero target write |
| N04 | changed source after plan but before replacement | zero target write |
| N05 | diff outside mapped range or more than one file | zero target write |
| N06 | add, delete, rename, binary, mode, project, script, or excluded path patch | zero target write |
| N07 | reparse point, path traversal, source/workspace overlap, or absolute path persistence | zero target write |
| N08 | missing, failing, superseded, or unaccepted verification evidence | zero target write |
| N09 | interrupted before journal, after journal, after backup, before replacement, after replacement, or before refresh activation | exact preimage or durable recovery-required state |
| N10 | refresh candidate or receipt validation failure after replacement | rollback or durable recovery-required state; no false current revision |
| N11 | concurrent apply attempt | one serialized result; no interleaved source state |
| N12 | tampered backup, journal, receipt, or historical revision | fail closed and block further apply |
| N13 | any Git index, ref, worktree, commit, or target metadata mutation by IGD | test failure |

## Regression And Performance Gates

- Run all P9.34 daily launch, bundle, install, and server checks when shared CLI,
  local-data, workspace, or launcher code changes.
- Run all P9.35 refresh positive/negative, revision, and WindowsUtility benchmark
  checks when shared source-digest, revision, or activation code changes.
- On the reference WindowsUtility export, after-candidate planning must remain within
  60 seconds and one-file source replacement plus local revision activation within 10
  seconds, excluding externally executed verifier duration.
- Before a real target run, prove the full matrix in an isolated disposable copy and
  compare target and `.git` trees before/after. IGD must not rely on `git status` as
  that observation may refresh Git index metadata.

## Review Questions

The P9.36 review must answer:

1. Which P8 experiment assumptions are unsafe or too narrow for the product path?
2. Why does the first G2 scope exclude multi-file application?
3. Which operation is source-authoritative, which is local-overlay-authoritative, and
   which requires an explicit human approval?
4. What exact evidence proves a post-apply source and active revision agree?
5. How does a crash recover without inventing a completed state?
6. Which G3 work remains before a real user-quality claim is allowed?

## Stop Rules

- No G2 implementation starts while an apply authority can be inferred rather than
  represented by an exact approval record.
- No G2 implementation starts while a failed multi-step operation lacks a truthful
  recovery state.
- No source-control command is added to the target write path without a new decision
  and test evidence.
- No real WindowsUtility write occurs in P9.36.
