## Stabilization Plan

1. Real-project repository readiness
   - Resolve or explicitly scope WindowsUtility's existing local state.
   - Re-run read-only inventory after the target state is acceptable.
   - Keep target writes blocked until a dedicated adoption slice authorizes them.

2. Mapping acceptance
   - Convert at least one WindowsUtility mapping hypothesis into an accepted Intent Unit mapping.
   - Preserve ambiguity records for unresolved module and hardware-coupling boundaries.
   - Add deterministic stale/missing mapping failure probes for accepted mappings.

3. Real change loop
   - Choose one low-risk WindowsUtility task.
   - Create a non-applied proposal first.
   - Verify mapping, evidence, authority, and rollback requirements before any source edit.

4. Evidence and authority
   - Define the human acceptance boundary for real-project changes.
   - Record evidence requirements before implementation.
   - Keep AI output proposal-only.

5. Real-project workbench
   - Emit a WindowsUtility-specific projection showing inventory, mappings, ambiguity, proposal, evidence, authority, and history.
   - Keep HTML/static preview acceptable until interaction requirements are explicit.

6. Product surface decision
   - Decide the first product surface only after the real-project loop succeeds.
   - Candidate order: CLI report commands, local static workbench, local app, editor integration, GitHub workflow integration.
   - Each surface needs its own prior-art/build-borrow-integrate review.
