# P9.35 Reviewed Source Refresh Review

## Decision

P9.35 passes at **Level 4 - Evidence-Bearing Slice**.

IntentGraph can now resume a local C# review project after external source changes
without silently treating prior mappings, proposals, verifier results, evidence
decisions, or history as current. It creates a deterministic non-applied candidate,
requires acceptance of one exact plan, preserves immutable predecessor workspaces,
and activates the accepted revision through one atomic launch-record pointer update.

This is not proposal application, automatic semantic migration, or target execution.

## Planned Boundary

The implementation followed the three gates fixed before completion:

1. `P9.35A`: deterministic source/fact/relation delta and validated candidate;
2. `P9.35B`: exact-plan accept/discard with immutable revisions and atomic pointer;
3. `P9.35C`: interruption probes, regressions, installed-runtime smoke, and a real
   WindowsUtility-scale benchmark.

## Delivered

- `igd refresh <source-root>` for a non-applied review plan;
- `--accept-plan <exact-id>` and `--discard-plan <exact-id>`;
- launch schema `0.2.0` with one active revision and contiguous historical revisions;
- read compatibility for existing P9.34 launch schema `0.1.0`;
- immutable candidate and accepted revision workspaces;
- source-file, code-fact, and relation deltas;
- retained/stale mapping classification by canonical code-fact equality;
- historical-only treatment for proposals, receipts, verifier results, and evidence
  decisions bound to the prior snapshot;
- work-item normalization for the new snapshot;
- refresh verification, evidence, receipt, and history records;
- path/reparse containment for refresh and revision storage;
- digest validation of active and every historical revision during normal launch/status;
- deterministic Windows bundle discovery of the new runtime module;
- installed-runtime refresh plan/discard/replan/accept smoke.

## Problems Found And Corrected

1. The first draft swapped workspace directories and wrote a separate index after the
   launch record. A process interruption could expose inconsistent authority. It was
   replaced with immutable revision workspaces and one atomic launch pointer commit.
2. The first candidate staging path could exceed Windows path limits. The staging
   hierarchy was shortened and the small-project lifecycle was rerun.
3. The first candidate state copied old evidence/history into the new active state.
   Snapshot-bound records now remain only in the predecessor revision.
4. Semantic-foundation fallback caught every validator exception and could hide
   unrelated corruption. Refresh now invalidates the old foundation explicitly and
   requires ordinary candidate validation to pass.
5. Reused pending plans initially did not revalidate active/candidate digests. They now
   revalidate both workspaces and the candidate project before reuse.
6. Refresh/revision child paths initially lacked their own junction check. Internal
   reparse paths now fail closed and have a dedicated Windows junction probe.
7. Historical workspace digests were recorded but not checked by normal status.
   Launch validation now rehashes every revision and detects historical tampering.
8. Acceptance initially checked source and launch provenance only near entry. Both are
   checked again immediately before the atomic pointer commit.
9. A staged revision and receipt initially had a small partial-state window. Workspace
   plus exact receipt now enter the revision path in one directory rename, and retries
   accept only an exact matching staged revision.
10. A P9.34 fail-closed error string changed during refactoring. The existing CLI
    contract was restored rather than weakening its regression.
11. Installed smoke could lose the real Windows error behind strict UTF-8 decoding.
    The runner now preserves diagnostics with replacement decoding.
12. A post-commit interruption could leave the accepted plan in `refresh/pending`;
    the original discard path could then remove the newly active revision directory.
    Discard now recognizes launch-bound accepted plans, removes pending metadata only,
    and returns `accepted-plan-cleanup` without deleting active or historical revisions.
13. Daily status initially read the pending plan without applying the full internal
    refresh-path/reparse and candidate-provenance checks. Status now validates the
    pending plan and candidate with the same fail-closed boundary used by refresh.
14. Revision source and activation digests were initially syntax-checked rather than
    rebound to the stored workspace and exact acceptance receipt. Launch validation now
    rehashes each revision workspace, binds its source digest to project state, and binds
    accepted revisions to their exact plan receipt and digest.
15. Receipt validation still allowed omitted authority/transition fields and a joint
    launch-plus-receipt digest forgery. Accepted revisions now retain the canonical
    plan and validate the exact receipt, transition, authority, and recomputed digest.
16. A workspace mutation between final pre-commit validation and launch replacement
    could activate an invalid revision. Acceptance now validates again after commit and
    atomically restores the prior launch pointer on a detected late mutation.
17. Status initially rejected a refresh-directory junction but still followed a
    plan-file symlink and did not rehash the candidate. Status, accept, discard, reuse,
    and no-change cleanup now share fail-closed plan/path/candidate checks.
18. Discard initially attributed an unreferenced revision using only `planId` and could
    recursively remove unrelated contents. It now requires the exact plan, receipt,
    workspace digest, project validator result, and exact root entry set.
19. Plan, receipt, and launch digests could be changed together while forging semantic
    delta fields. A shared deterministic model now recomputes candidate state,
    source/fact/relation deltas, invalidation, and preservation from predecessor/current
    workspaces during both acceptance and ordinary launch validation.
20. The live WindowsUtility working tree changed concurrently during one benchmark run.
    The run failed correctly; final evidence uses a read-only local Git `HEAD` export so
    user changes are neither touched nor misattributed to IGD.
21. The hand-maintained milestone review report became stale after hardening. A
    deterministic emitter now validates all subordinate evidence and derives every
    count, digest, threshold result, and benchmark value.

## Prior-Art Comparison

P9.35 borrows immutable identity/history from Git, staged candidate construction and
atomic pointer replacement from transactional systems, and content-digest invalidation
from build/index systems. It does not replace Git or build a new indexer. Its distinct
work is the reviewed classification and preservation of IntentGraph mappings, work
items, proposals, evidence decisions, authority, and semantic history around one
external source transition.

## Preserved Boundaries

- no target source mutation by IGD;
- no proposal application or automatic proposal migration;
- no automatic intent mapping, evidence acceptance, or approval;
- no target build, restore, test, or launch;
- no provider, credential, external network, signing, or release operation;
- no absolute source path persisted;
- no renderer or graph-visualization change.

## Remaining Product Gaps

- revision digest validation is intentionally linear in revision count; larger history
  will need measured indexing or bounded verification without weakening tamper evidence;
- retained mapping is exact-fact equality, not semantic remapping;
- stale proposals require human reauthoring or a future reviewed revalidation workflow;
- installer upgrade/repair/rollback remains absent;
- the daily product still cannot apply an accepted proposal to source;
- host Python and .NET SDK remain required;
- public signing, release, editor, GitHub, and team workflows remain absent.
