## Scope

P3.3 reviews P3.0 through P3.2 as a Phase C sequence. It decides whether B1 intent mapping is stable enough to begin proposal-only change planning.

This slice is review/plan-only. It does not add source edits, code planning implementation, AI proposal generation, ambiguity resolution, UI/workbench, productization, or broad extraction.

## Reviewed Evidence

P3.0 proved:

- B1 intent mapping schema v0 exists.
- B1 static overlay maps behavior, route, contract, and verification units to code facts.
- accepted mappings require code refs, code fact refs, mapping obligations, evidence, and authority.
- mapping verifier and negative probes reject bad accepted mappings.

P3.1 proved:

- stale accepted mappings fail deterministically when a mapped code fact disappears.
- the stale failure is visible through a dedicated probe report.

P3.2 proved:

- ambiguous mapping candidates can be represented outside the accepted overlay.
- candidate facts resolve while the candidate remains unresolved.
- ambiguity, AI generation, authority grant, and accepted-into-overlay claims are blocked unless a later authority flow exists.

## Phase D Entry Criteria

Phase D may open only as a bounded B1 proposal slice.

The first Phase D slice must:

- define a B1 change proposal schema
- create a non-applied change proposal artifact
- declare proposed `DeltaC`, `DeltaI`, and `DeltaM`
- declare required tests, evidence, and authority
- bind the proposal to exact source/code-fact baselines
- reject overbroad impact scope, stale baselines, missing tests, missing evidence, missing authority, and self-authorized proposals
- keep proposal generation separate from proposal acceptance and application

The first Phase D slice must not:

- mutate B1 source code
- apply patches
- accept AI proposals as authority
- resolve ambiguous mappings automatically
- build a broad planner
- build a workbench UI
- broaden extraction
- productize the workflow

## Recommended P4.0 Slice

```text
P4.0 B1 Change Proposal Schema and Non-Applied Plan
```

P4.0 should use a small planned change, such as adding a `complete todo` route over the already-present `completeTodo` service fact, but it must remain proposal-only. The expected output should be an inspectable artifact describing code edits, mapping updates, test requirements, evidence requirements, and authority requirements without changing source bytes.

P4.0 should add deterministic validation and negative probes for:

- stale source or code fact baseline
- overbroad edit scope
- missing mapping update proposal
- missing test requirement
- missing evidence requirement
- missing authority requirement
- self-authorized or AI-authorized proposal
- accidental source mutation claim
