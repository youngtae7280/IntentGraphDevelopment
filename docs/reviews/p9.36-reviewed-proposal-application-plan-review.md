# P9.36 Reviewed Proposal Application Product Gate Review

Date: 2026-07-14
Decision: G1 plan-only gate passes. G2 may be implemented only as a reviewed,
single-file C# application transaction after a separate implementation authorization.

## Evidence Reviewed

| Evidence | Value | Product limitation |
|---|---|---|
| P8.41 dry-run | deterministic scoped preview, rollback/evidence/authority rehearsal | no code patch or target write |
| P8.43 preview | one low-risk patch preview with build plan | manually selected target-specific change |
| P8.44 application | one test-automation source edit, build, commit, and push | not a reusable IGD product flow |
| P8.45 review | first real loop evidence | explicitly not product readiness |

## Decision

The product must not reuse P8.44's direct target-edit approach. It lacks a reusable
proposal approval identity, staged post-apply refresh candidate, transaction journal,
crash recovery contract, and explicit separation between verifier evidence and source
application authority.

P9.36 therefore selects a single existing mapped `.cs` file as the first G2 scope.
This is not an arbitrary limitation: it allows the source replacement itself to be an
atomic same-directory replacement, while multi-file state remains an explicit future
transaction problem rather than an untrue all-or-nothing claim.

Git is treated as a history and patch-semantics reference, not an implementation
dependency. In particular, G2 rejects `git apply --index`, `git apply --3way`, and
worktree/index operations because IGD must not mutate target Git metadata.

## Remaining Risks

- A local declared maintainer approval is not cryptographic authentication.
- External verification evidence remains a separate authority boundary.
- One-file application is intentionally not proof of multi-file transactional writes.
- Workbench visual acceptance remains deferred to G6.

then obtain a separate explicit authorization before any real WindowsUtility source
