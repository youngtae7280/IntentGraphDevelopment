# P9.18 Large-Graph Navigation and Performance Workbench Review

Date: 2026-07-13

## Decision

P9.18 passes the bounded Workbench responsiveness correction for the WindowsUtility local projection.

The review responds to two observed failures: source communities looked mechanically arranged, and ordinary lens/search/selection interactions paid a full-graph restyling cost. The correction keeps the complete graph present while making navigation operate on small, explicit deltas wherever possible.

## What Changed

- source communities are ordered by code-fact volume and placed with deterministic nested golden-angle spirals for module, file, and symbol layers;
- the Cytoscape instance is created once for the full projection;
- complete and semantic identity sets are cached, avoiding full visibility-set reconstruction for Full and Semantic lens transitions;
- overview zoom suppresses only raw `code-relation` painting; all records remain loaded and semantic/capsule/mapping/delta relations stay visible until raw syntax detail is useful;
- Semantic overview is an emphasis lens over the complete graph, not a destructive semantic-only graph replacement;
- text search highlights matches in place rather than hiding unrelated facts while typing;
- visibility updates compare the prior and next sets before touching Cytoscape elements;
- selection styles only the selected element and direct relationships;
- ordinary lens and filter changes preserve the current viewport; only an explicit `Fit` reframes the graph;
- resize handling is animation-frame limited and does not force a graph-wide fit;
- fit uses stored deterministic positions rather than a graph-engine element scan.

## Evidence

The local WindowsUtility projection remains:

- 8,188 nodes and 8,040 relations;
- 8,137 syntax-only code facts and 17 code capsules;
- 18 declared semantic-foundation records;
- one explicit work/Intent/mapping/proposal chain.

In the checked local browser run after the correction:

- semantic/full lens changes completed in approximately 0.33 seconds, and one zoom command completed in approximately 0.30 seconds; the remaining cost is a single canvas redraw of the unchanged node scene, not a new graph build or force layout;
- a `CsdBrowseService` search completed in approximately 0.20 seconds, kept all 8,188 records loaded, and highlighted 29 matches rather than reducing the graph to 29 nodes.

Those timings describe the checked local machine/browser and are regression observations, not a hardware-independent performance claim.

## Verification

- project Workbench emission validates from the unchanged local project workspace;
- JavaScript parsing of the emitted Workbench succeeds;
- loopback server smoke verifies deferred HTML plus the organic-layout, in-place search, selection-neighbor, and differential-visibility markers;
- semantic-foundation negative probes remain passing and leave project state unchanged;
- B1 local-review regression remains passing;
- browser checks confirm the full graph, semantic emphasis, search highlighting, and lens return path remain nonblank and interactive.

## Non-goals and Remaining Gap

P9.18 does not prove a WebGL renderer, a universal large-repository threshold, resolved C# call semantics, reviewed foundation editing, interactive proposal authoring, controlled evidence execution, editor integration, multi-user coordination, or distributable packaging.

It does prove that the current full-graph product surface no longer needs to choose between topology visibility and ordinary navigation responsiveness for the measured WindowsUtility snapshot. The next product slice should improve the integrated request-to-proposal-to-evidence workflow, not add another isolated graph viewer.
