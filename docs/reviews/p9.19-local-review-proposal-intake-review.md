# P9.19 Local Review Proposal Intake Review

Date: 2026-07-13

## Decision

P9.19 passes the bounded local proposal-intake gate.

Before this slice, a user could record a work request and mapping candidate in the loopback Workbench, but had to leave the product surface and use a CLI artifact path to introduce the review proposal that connects the work to graph delta, code diff, evidence, and verification requirements.

The Workbench now accepts a user-pasted proposal document through the loopback server. The server calls the existing P9.14 proposal validator and records the artifact only on success. The proposal remains non-applied and review-required.

## Evidence

- `tools/run_experimental_csharp_project_server_smoke.py` passed 15 probes.
- The smoke creates a fresh local request and mapping, records a valid review proposal, reloads the resulting delta projection, rejects an `applied` status claim, and proves snapshot provenance unchanged.
- `tools/run_experimental_csharp_change_proposal_negative_probes.py` passed all 8 existing proposal-contract probes.
- Python compilation and inline Workbench JavaScript parsing passed.

## Product Result

The Workbench now supports the complete local review handoff:

```text
work request -> declared code mapping -> review-only proposal -> inspectable graph delta and code diff
```

This is intentionally proposal intake, not proposal generation. A person or an external drafting process must still provide the artifact. That preserves the distinction between AI-authored candidate content and deterministic acceptance/recording.

## Remaining Gap

P9.19 does not provide reviewed mapping acceptance, controlled evidence execution, source application, editor integration, multi-user collaboration, or distributable packaging. The next workflow slice should make proposal verification/evidence requirements actionable without allowing source mutation or self-approval.
