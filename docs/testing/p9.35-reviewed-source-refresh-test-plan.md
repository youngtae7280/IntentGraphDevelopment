# P9.35 Reviewed Source Refresh Test And Validation Plan

## Test Thesis

Given a valid active local C# review workspace and externally changed source, IGD can
produce a deterministic, non-applied refresh plan and can activate its candidate only
after exact user acceptance, while preserving the previous full revision and making
all stale snapshot-bound records explicit.

Declared milestone quality: **Level 4 - Evidence-Bearing Slice**.

## Work Breakdown And Gates

### P9.35A - Plan Boundary

Implement and validate `igd refresh <source-root>`.

Pass conditions:

- source delta, code-fact delta, relation delta, stale records, and preservation data
  are present and deterministic;
- candidate workspace passes the normal workspace validator;
- active workspace, launch record, revision index, and target source are byte-stable;
- a repeated request reuses the same plan;
- a no-change request returns `not-required` without a pending candidate.

Do not start P9.35B if any condition fails.

### P9.35B - Acceptance And Archive Boundary

Implement and validate `--accept-plan` and `--discard-plan`.

Pass conditions:

- the exact plan id is required;
- source, active workspace, candidate workspace, launch, and revision-index drift are
  rejected before active mutation;
- the prior full workspace is sealed and the transition receipt is recorded;
- the new active workspace and old archived workspace both validate;
- stale records are absent from active state and present in the archive;
- retained mappings and normalized work-item states match the plan;
- revision sequence and digests are internally consistent;
- an injected failure before the atomic pointer commit leaves the prior revision
  active, while an injected failure after the commit leaves the new revision active.

Do not start P9.35C if any condition fails.

### P9.35C - Hardening, Regression, And Benchmark

Pass conditions:

- repeatable positive and negative harnesses pass;
- P9.34 daily launch, server, bundle, and installed-runtime regressions pass;
- two consecutive accepted refreshes preserve a contiguous revision chain;
- repeat plan generation after discard is semantically byte-identical;
- WindowsUtility-scale plan completes within 60 seconds and acceptance within 10
  seconds on the current reference machine;
- the benchmark copy and original WindowsUtility source remain byte-identical outside
  the intentional temporary benchmark mutation;
- no network, provider, credential, target build, restore, or launch occurs.

## Positive Scenarios

| ID | Scenario | Expected result |
|---|---|---|
| R01 | unchanged source | `not-required`, zero pending writes |
| R02 | one file changed | review-required plan with changed file/facts/relations |
| R03 | file added | added source/facts/relations classified |
| R04 | file removed | removed source/facts/relations and stale mappings classified |
| R05 | unchanged referenced fact | mapping retained |
| R06 | changed/removed referenced fact | mapping stale and archived |
| R07 | active proposal lifecycle records exist | proposal/receipt/result/decision stale and archived |
| R08 | repeat plan request | same plan id/digests, no replacement |
| R09 | discard exact plan | pending removed, active unchanged |
| R10 | accept exact plan | old revision archived, candidate active |
| R11 | second refresh | contiguous `r0001 -> r0002 -> r0003` chain |
| R12 | status during review | `refresh-review-required` with exact plan id |
| R13 | status after accept | normal `pass` state resumes |

## Negative Scenarios

The harness must fail closed for at least:

- wrong plan id for accept and discard;
- source drift after planning;
- active workspace drift after planning;
- candidate workspace drift after planning;
- launch-record drift;
- malformed plan role, schema, scope, status, authority, or revision transition;
- missing or malformed revision index;
- archive collision or revision sequence gap;
- path traversal, symlink, source overwrite, output collision, or source-path
  persistence;
- stale mapping retained as active;
- snapshot-bound proposal or evidence decision retained as active;
- candidate workspace validation failure;
- simulated activation failure immediately before and after the launch pointer commit;
- exact discard after a post-commit interruption cleans only pending metadata and
  cannot remove an active or historical revision;
- status and refresh both reject an internal refresh reparse/junction path;
- historical workspace byte tamper and archived source-provenance tamper;
- accepted revision receipt or exact plan-digest provenance tamper;
- target source mutation by any IGD operation.

Every negative probe must record `expectedFailureObserved: true` and the expected
failure substring. Unexpected success is a test failure.

## Deterministic Assertions

The committed P9.35 report must include:

- role, schema, scope, result, and exact test count;
- source bytes before/after each operation;
- active/candidate/historical revision tree digests;
- plan id and canonical plan digest;
- source/fact/relation delta counts;
- retained/stale mapping and lifecycle record counts;
- active/archive validator results;
- pre-commit and post-commit interruption results;
- revision sequence result;
- repeat-emission equality result;
- regression command results;
- WindowsUtility plan and accept wall-clock measurements;
- all authority and non-goal flags.

## Manual Review

No visual review is required for P9.35. The coordinator reviews the JSON plan fields,
one archive, one active state, and the milestone review. A human must be able to tell:

1. what source changed;
2. which facts and relations changed;
3. which mappings and proposals became stale;
4. what remains preserved;
5. which exact revision will become active;
6. that the target source was not modified.

## Stop And Repair Rules

- Any active write during planning is a P1 defect: stop, repair, rerun all P9.35 tests.
- Any lost or silently-current stale record is a P1 defect.
- Any source mutation, automatic approval, or drift acceptance is a P1 defect.
- Nondeterministic output, invalid archive, failed rollback, or broken P9.34 regression
  is a P2 defect: stop before the next milestone and repair.
- Performance above the declared ceiling is a P2 defect until profiled and corrected
  or the threshold is revised with measured justification.
- Do not mark P9.35 complete or choose P9.36 while any P1/P2 defect remains.
