## Scope

P8.2 defines how P7.2 read-only mapping hypotheses may become accepted real-project Intent Unit mappings.

This slice is plan/report-only. It does not accept a mapping, mutate WindowsUtility, inspect untracked `.devview/` contents, apply proposals, run AI code generation, or authorize productization.

## Inputs

- P7.1 read-only WindowsUtility inventory
- P7.2 WindowsUtility mapping hypotheses
- P8.1 unresolved repository state boundary

## Accepted Mapping Requirements

An accepted WindowsUtility mapping must include:

- selected hypothesis id
- accepted Intent Unit id
- source file/code surface refs
- source digest baseline
- explicit ambiguity disposition
- evidence requirements
- authority requirements
- stale/missing mapping negative probes
- no source text equality requirement
- no hidden generated-code snapshot
- no target write authority

## Acceptance Workflow

1. Select one candidate hypothesis from P7.2.
2. Resolve all referenced source files against a recorded inventory baseline.
3. Record whether the target repository state is clean/aligned or explicitly accepted as a dirty read-only baseline.
4. Resolve or defer each ambiguity record.
5. Declare evidence and authority requirements.
6. Emit an accepted mapping artifact outside the WindowsUtility repository.
7. Run deterministic stale/missing mapping failure probes.
8. Keep proposal application and target writes blocked until a later adoption slice.

## Blocking Conditions

Accepted mapping work must block if:

- target state is treated as clean when it is not.
- a hypothesis is accepted without source refs and digest baseline.
- ambiguity is silently ignored.
- evidence or authority requirements are missing.
- stale/missing mapping failures are not deterministic.
- the accepted mapping artifact is written inside WindowsUtility without explicit approval.
- the mapping grants proposal application, AI authority, or productization.
